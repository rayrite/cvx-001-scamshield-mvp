# ScamShield Recall Check — smoke test first, then routed staged recall research

Recall questions fail in two familiar ways: a vibes answer ("never heard of a recall, you're fine") that missed the FDA notice from three weeks ago — or an unstructured trawl that drowns the user in aggregator SEO pages of unknown vintage. This skill splits the difference in **three tiers**. **Stage ½ smoke test**: a zero-search pass over the supplied material — if the user brought a message, post, site, or article *claiming* a recall, a seasoned reader flips to the payment ask, the sender domain, or the phone number and knows in seconds whether the **content** is a fake-recall scam; a decisive tell delivers the verdict immediately (snap verdict). The smoke test can **never** answer "is this product recalled" — that always takes the routed sweep. **Stage 1 routed triage**: a light snippet-first sweep across the check lines that matter for the product class — the correct federal agency list first (FDA for most food; FSIS for meat/poultry/processed egg; CPSC for consumer products; NHTSA for vehicles…), then the CDC outbreak layer, state distribution pages, retailer hubs, and press. **Verify stages**: fetch the agency record, the state distribution list, the lot-level retailer entry — but only when the user orders them, one bounded stage at a time.

Every check ends with **two readouts**, because they answer different questions: **Recall status** (always rendered — the product's documented record) and **Content authenticity** (only when the input is claim-bearing content — is this message/post/article/site what it claims to be). A post can be authentic AND the product recalled; a recall text can be a scam about a never-recalled product. Never collapse the two into one verdict.

## When to scope down

Not every question needs the machinery. "Does FSIS cover cheese?" gets an answer from the source guide — no stages. "What's a Class I recall?" gets an explanation — no stages. The full workflow is for checking a **specific subject**: "is my brand of almond milk recalled", "check this lot code", "is this recall text real", "did anyone get sick from this". One subject = one check; if the user drops a bundle (an article claiming a recall about a product), treat it as ONE investigation — the product is the primary subject, the article's claim is evidence to verify. "Which of these three products has been recalled" = separate checks, one file each.

## Key concepts

- **Smoke test (Stage ½)** — zero-search checklist of decisive static tells on claim-bearing content: refund-payment asks, agency/brand domain mismatches, call-center funnels, look-alike "official recall" sites. Any decisive tell → **snap verdict** on the authenticity readout (🔴, High, labeled `snap`), no research, no report file. Full checklist and rules: `references/smoke-test.md`.
- **Subject types** — the six things this skill checks: `product/food name`, `SKU/lot/UPC code`, `product website`, `social post` (TikTok/Facebook/Instagram), `news article`, `recall message` (text/email/DM). Stage 0 classifies the subject and loads **only the matching guide** from `references/subject-check-guides.md`.
- **Product-class routing** — the fact that makes recall research work: which agency regulates the item determines where the record lives. FDA ↔ FSIS ↔ CPSC ↔ NHTSA ↔ FDA-drug/device ↔ USCG ↔ EPA, plus the CDC outbreak layer ("no recall yet but people are sick") and the state layer ("was it distributed here?"). Full routing matrix and every source URL: `references/recall-source-guides.md`.
- **Check lines** — the 8 standard verification dimensions: R1 Agency recall list (routed) · R2 Agency databases & archives (Enforcement Reports, device DB, CPSC by-company) · R3 CDC outbreak layer · R4 State distribution layer (~30 states maintain lists) · R5 Retailer & manufacturer layer (lot-level, non-authoritative) · R6 Press & news record · R7 Content authenticity (claim-bearing subjects only) · R8 Community record. Not all apply to every subject — the guides give the priority order.
- **Two verdict readouts** — Recall status: 🔴 recall record found · 🟠 recall-adjacent (withdrawal / safety alert / outbreak investigation) · 🟡 unverified or ambiguous identity · 🟢 no recall record found. Content authenticity (claim-bearing only): 🔴 scam/impersonation pattern · 🟠 multiple red flags · 🟡 unverifiable · 🟢 no adverse findings. Bands, anchors, and honesty rules: `references/verdict-rubric.md`.
- **Coverage map** — per-check-line status: ⚪ unchecked · 🔵 checked, clean · 🚩 checked, flagged · 🔴 checked, hit · ➖ not applicable. The honesty device: a 🟢 "no recall found" is only worth its coverage.
- **Ripeness & relevance gauge** — per-line and overall readout of how much *new* decision-relevant evidence one more verify stage would surface: 🟢 75–100 fresh · 🟡 50–74 yielding · 🟠 25–49 thinning · 🔴 0–24 exhausted, each scored from ledger signals (novelty rate, lead-pool depth, tier-ceiling gap) and each line rated for relevance to the user's situation. Stage-1 scores are prospect estimates. The gate's price tag, kept strictly separate from both verdict readouts. Full rubric and formats: `references/ripeness-rubric.md`.
- **Research ledger** — query log, findings index, lead pool, verdict history, gauge history, persisted in the report file. What makes multi-stage checks work without repeating searches.
- **Output mode** — where the full stage content goes: `file` (default — highlights in chat, full cumulative report in the report file) · `chat` (the complete content of every stage prints to the chat response; no file unless requested) · `both`. Default set by `recall-check.config.json` (`"output_mode"`, alongside `"overview_map"`; absent file = `file`) ; the user's in-chat choice always wins and is noted in the report meta. Formats: output contract.
- **Overview map (optional post-processing)** — geocode-accurate U.S. map of locations named in the findings (outbreak case counts, distribution states, incident reports), rendered from real coordinates on a real basemap — never a generated illustration. Emitted as a **modular, embeddable component**: the HTML works standalone and drops into a host app (iframe · `<recall-overview-map>` element · `RecallOverviewMap.create` API), with scoped styles, theme tokens (light/dark), and responsive layout for desktop and mobile. Default **ON during beta**; toggle via `recall-check.config.json` (`overview_map`); in-chat override ("no map this run") always honored. Full pipeline, schema, template, and embedding guide: `references/overview-map.md`.

## Safety rules (read before any check)

- **Suspect claim-bearing material = static analysis only.** For a recall message/email/DM or a suspect site: never click its links, never reply, never call its numbers, never enter data. Extract domains/URLs as *text* (defanged: `recall-refund[.]com`) and reputation-check them via search, not by fetching.
- **Product sites = passive inspection only.** Fetching public pages to inspect is fine. Never enter payment data, create accounts, or download files from a subject under investigation.
- **Consumer-safety posture.** If the user (or a pet) already ate/used the product: lead with safety, not research — stop using the item, keep the packaging (lot codes), follow the agency's remedy instructions, seek medical/veterinary guidance for symptoms, and report illness to the local/state health department (that is what triggers CDC investigations). Report product problems to the routed agency portal (source guide §1).
- **Verdict discipline.** Evidence-linked language: "FDA recall notice dated 2026-08-12, Class II, undeclared milk" not "this product is dangerous garbage". Distinguish *documented* (agency record, CDC investigation, dated press naming specifics) from *inferred*. Never call a product unsafe beyond what the record shows; never call a message fraudulent beyond its observed tells.
- **No fabrication.** Every cited recall, alert, or outbreak must exist in fetched or snippet-verified results with its date. Absence of a record is reported as "no recall record found across <lines>", never as "safe". Never invent lot codes, dates, or case counts.
- **Redact the user's PII** (name, address, order numbers, purchase details) when quoting their material into the report file.

## Inputs to collect

- **Subject + exact identifiers** — product/food name AND brand; SKU/UPC/lot/batch/best-by date if the user has the package; URL (site or post) or the message text pasted verbatim; article headline/URL. If the user names a category ("some lettuce"), ask once for the specific brand/product; one clarification round max, then commit.
- **Region / market** — default US (this skill's source base is US-only); note honestly when the subject is non-US and coverage will be thin.
- **User's situation** — *screening* (deciding whether to buy/eat — the default) or *already owns/ate/used* (→ consumer-safety path in Stage 0) or *already clicked/paid in response to a recall message* (→ victim path: preserve evidence, card-issuer dispute, FTC/USPIS report, recovery-fraud warning).
- **User's angle** — current recall only, or full history including past recalls? Default: both, clearly separated by date.
- **Output location** — default `recall-check_<slug>_<YYYY-MM-DD>.md` in the working directory; use the user's path if given.
- **Output mode** — `file` / `chat` / `both` (default `file`, from `recall-check.config.json` alongside `"overview_map"`; editing the default in this bullet changes the skill's baked-in default). State the active mode once at intake — e.g. *"Full report → file (default). Say 'in chat' to print full stages here, 'both' for both."* — and honor any-time switches for the rest of the check.
- **Today's date** — anchor time-sensitive queries to it (`<brand> recall 2026`, `<product> recalled <current month>`). Recall records are dated facts; undated aggregator pages are the noise this skill exists to route around.

## Procedure

### Stage 0 — Intake (no searching)

1. Capture today's date as `YYYY-MM-DD` and the subject's exact identifiers. Reason: recall pages change daily; a record's *dates* (announced, expanded, concluded) are half the answer.
2. Classify the subject type (product name / SKU-lot / website / social post / news article / recall message; bundle rule above) and read **only the matching guide** in `references/subject-check-guides.md`.
3. **Route the product class** using the matrix in `references/recall-source-guides.md` §1 — this fixes R1's target surface (e.g., ground beef → FSIS, not FDA). If the class is unclear (a supplement? a prepared food with meat?), the sweep's first job is class identification, and the routing is revisited before R2+.
4. **Consumer-safety / victim-path check:** if the user already ate or used the product — run the check, but center the first response on the safety steps above. If the user already responded to a suspect recall message (clicked, paid, gave card data) — center on damage control: preserve the message, dispute the charge, report it (FTC ReportFraud.ftc.gov; the impersonated agency/brand), and warn that recovery-fraud follow-ups target people who just reported scams.

### Stage ½ — Smoke test (zero searches, target: seconds)

5. Run the smoke checklist from `references/smoke-test.md` over the supplied material — but **only if it is claim-bearing content** (a message, post, site, or article asserting a recall or refund). A bare product name or lot code has nothing to smoke-test: fall through immediately. **Zero network calls.**
6. **If any [Decisive] item fires:** deliver the snap response immediately — authenticity verdict box (🔴, High, labeled `snap`), the fired tells with item IDs, 2–3 do/don't bullets, and the gate with the `document` option. The **recall-status readout is explicitly marked "not checked"** — a fake message about a product does not tell us whether that product has a *real* recall record, and `document` is what checks it. **No searches, no report file.**
7. **If only [Corroborating] items fire:** carry them into Stage 1 as opening findings. **If nothing fires:** Stage 1 unchanged. The smoke test must never make thin evidence feel decisive, and must never imply a product is recalled (or not) from the content's authenticity alone.

### Stage 1 — Routed triage (light and fast)

8. Run **8–12 parallel web searches**, snippet-first, spread across the routed check lines per the subject guide: the R1 agency-list sweep (`site:fda.gov <brand> recall` / `site:fsis.usda.gov <brand>` / `site:cpsc.gov <brand>` per routing), the R3 CDC check (`site:cdc.gov <food> outbreak`), the R6 news sweep (`<brand> <product> recall <year>`), plus subject-specific queries from the guide. **Fetch at most 3–5 pages** — the agency recall page itself, the CDC investigation page, or the one hit worth confirming. **No subagents.** Reason: Stage 1's promise is a fast routed verdict preview; every fetch it skips is time saved deciding whether to dig.
9. Record findings with their dates and specifics (agency, class, lots, scope, remedy, case counts). Write the **coverage map** and the provisional **two-readout verdict** per the rubric — Stage-1 verdicts are always labeled provisional (snap verdicts, which precede this stage, are labeled `snap`). Reason: "FDA Class II recall notice, 2026-08-12, undeclared milk, lots 24-081..24-084" is checkable and defensible; "sounds like it was recalled" is neither. Score the initial **ripeness gauge** per `references/ripeness-rubric.md` — a prospect estimate, labeled as such. Reason: the go/stop decision needs both what the record shows (verdicts) and whether digging further pays (yield).
10. Create the **report file** now — meta header, subject profile, verdict boxes, evidence by check line, coverage map, recommended actions, and the full ledger (query log, findings index, lead pool, verdict history, gauge history). In `chat` output mode, skip the file — the Stage-1 response carries the full stage content per the output contract; a file requested mid-check catches up at the next stage boundary. Reason: the file is the state container; a later session resumes from the ledger without re-searching.
11. Deliver the Stage-1 chat response: verdict boxes (recall status first), key findings with dates, coverage map, ripeness gauge + overall line, recommended actions, default Stage-2 plan, command hint. In `chat`/`both` output mode, this response carries the full stage content instead (output contract).

### Between stages — the gate

12. End every stage response with the plan and this hint, verbatim in spirit: `Reply "go" to run this plan · describe a different direction to customize · "stop" to finalize the recall background-check report.` After a **snap verdict**, the gate reads: `Say "document" for the full archived report — which also checks <product>'s actual recall record · describe a different direction to customize · "stop" to finish here.`
   - `go` / `check` / `next` / `continue` / `dig` / `yes` → execute the default plan verbatim. Do not re-plan, do not re-ask.
   - `document` (after a snap verdict) → run the documentation pass: the Stage-1 routed sweep (step 8) against the subject — both documenting the scam pattern AND answering the recall-status question honestly — write the full report file, deliver the Stage-1-style response.
   - Substantive text → custom stage: restate your interpretation in one line, plan to match, execute. Ask one question only if genuinely ambiguous. Map overrides ("no map this run" / "add the map") are honored silently and noted in the report meta.
   - `stop` / `done` / `enough` / `finish` → consolidate (step 17). After a snap verdict with no documentation requested, consolidation = a final one-paragraph verdict confirmation; the file was never created, so none is needed.
   - `go` when coverage is already complete on all applicable lines, **or when the overall ripeness gauge reads 🔴** → push back **once** with the evidence (last stage's novelty rate, empty lead pool), offer the single most-targeted option; if the user insists, run a minimal stage.

### Stage N (N ≥ 2) — Verify

13. Execute the approved plan. Default budget: 8–12 searches + 4–8 fetches; one subagent per target check line, spawned in parallel when available, serial otherwise. Typical targets: fetch the agency recall notice page for full lot/class/remedy detail; the CDC investigation page for case counts and states; the state distribution list; the retailer hub entry for lot-level confirmation.
14. Enforce ledger discipline — **never re-run a logged query**; check the findings index before recording (a repeat is corroboration attached to the existing finding ID); park promising unfetched results in the **lead pool** instead of chasing them mid-stage.
15. Record findings as: one-line finding + source name + URL + access date + check line + confidence tag (`[Documented]` agency/CDC/government record · `[Reported]` press or retailer record naming specifics · `[Inferred]` signal-cluster match, no record yet). Contradictions (an "active" recall that's actually concluded; two agencies' counts differ) are surfaced explicitly, never silently resolved.
16. Close the stage: update the report file, **re-score the verdict, coverage, and ripeness gauge** for every touched line, then deliver the stage response: banner, 3–6 new findings (🆕), verdict boxes, coverage map, ripeness gauge + overall, next default plan (ordered by relevance × yield), command hint. In `chat`/`both` mode the stage response carries the full stage content (every finding, full citations) per the output contract, and the report-file update is skipped in `chat` mode.

### Consolidate

17. On stop: restructure the report file (if one exists) into the final background check — verdicts with confidence and evidence chains; findings grouped by theme; current vs past recalls clearly separated by date with conclusion status; recall-adjacent findings (withdrawals, alerts, outbreaks) in their own section; what was checked vs not; recommended actions (stop using / check lots / return per remedy / monitor outbreak page / ignore-and-report the scam message); where to report; gaps & caveats; tiered sources. Chat response: verdict boxes, one-paragraph basis, final gauge statement (why further stages would not pay — or what remains open), file path (or "no file was needed — snap verdict stood on direct observation") — in `chat`/`both` mode the full final report is delivered in the chat response instead (or in addition). The consolidated file must stand alone for a reader who never saw the stages — in `chat` mode, that reader reads the chat.
18. **Overview map post-processing** (this is step 18's own rule set): after consolidation, if the overview map is enabled (config default ON; `recall-check.config.json`; in-chat override) AND the findings name ≥1 U.S. location worth plotting — run the pipeline in `references/overview-map.md`: build the location table, geocode in tiers, dedupe, render the interactive HTML map plus the CSV/JSON table, verify the render **at both a desktop (≥1300×800) and a mobile (~390×844) viewport** — the artifact is a responsive, embeddable component and must hold up in a host chat UI, not just full-screen — and reference all three artifacts in the report. If no U.S. locations surface, or the map is disabled, state that plainly in the report's map section — never render a map with nothing honest to plot, and never plot a pin that geocoding didn't place.

## Output contract

- **Snap verdicts:** ultra-short chat response per `references/smoke-test.md`; **no report file** unless `document` is requested. When requested, the file is the Stage-1 file with the snap verdict as its authenticity verdict box, the recall-status verdict from the sweep, and the smoke items recorded as findings.
- **One cumulative report file** for staged checks, `recall-check_<slug>_<YYYY-MM-DD>.md` (creation date; collision → `-v2`), updated every stage, finalized on stop. In `file` mode (the default), never paste the full file into chat — link it and summarize.
- **Output modes** (default `file`; precedence: the user's in-chat choice > `recall-check.config.json` → `"output_mode": "file" | "chat" | "both"` alongside `"overview_map"`, absent file/field = `file` > this contract's default):
  - `file` — chat responses are highlight summaries (verdict boxes, key findings, coverage map, gauge, plan); the full cumulative report lives in the report file.
  - `chat` — the complete content of each stage prints to the chat response: stage banner, **every** finding recorded this stage with its full citation (finding + source + URL + access date + check line + confidence tag — no 3–6 cap), both verdict boxes when applicable, coverage map, ripeness gauge with legend, the stage's **ledger delta** (queries run, new finding IDs, lead-pool changes — the cumulative ledger is not reprinted, only the delta), then the plan. No report file is written unless requested; consolidation delivers the full final report in chat.
  - `both` — full stage content in chat **and** the report file maintained as in `file` mode.
  - Snap responses are unchanged in every mode (nothing exists yet to expand); the `document` pass follows the active mode. Map artifacts, when produced, are always files (they are rendered components) and are linked regardless of mode — the map is post-processing and unaffected by output mode.
- **File sections, in order:** meta header (subject · type · product class + routed agency · region · created · last updated · stage count · status · map on/off + how set) · Verdict Boxes (recall status; authenticity if applicable) · Subject Profile · Evidence by Check Line (H3 per line; findings cited; 🆕 marks current-stage additions) · Current vs Past Recall Record · Recall-Adjacent Findings · Coverage Map · Ripeness Gauge (current table + overall line) · Recommended Actions · If Already Consumed / If Victim: Next Steps · Where to Report · Gaps & Caveats · Overview Map (table path + map path, or why none) · Sources (tiered, with access dates) · Appendices A–E: the ledger (A queries · B findings · C leads · D verdict history · E gauge history).
- **Map artifacts** (when produced): `recall-check_<slug>_<YYYY-MM-DD>_map.html` (interactive component — standalone in any browser, embeddable in a host app via iframe / `<recall-overview-map>` / `RecallOverviewMap.create`; responsive desktop + mobile; scoped styles with `--rm-*` theme tokens), `_locations.csv`, `_locations.json` (the data of record — the component renders from this schema alone) — all three referenced from the report file.
- **Every stage's chat response ends with the verdict blocks, then the ripeness gauge (with legend), then the plan block.** Verdict legend rendered every time — a reader joining at Stage 3 must understand 🟠 without archaeology.
- **Citations:** inline Markdown links with the source name visible and access date; every non-trivial finding cited. Aggregator-sourced facts are labeled as such and must be confirmed at the agency page before driving a 🔴.
- **No fabricated anything.** If a check line came back empty, that's the finding — recorded in coverage, echoed in Gaps & Caveats.

## Source hierarchy (use in this order of preference)

1. **Federal agency record (.gov)** — the source of record: recall notice, class, lots, scope, remedy. Routed by product class (source guide §1–§2).
2. **CDC outbreak/investigation records** — the "no recall yet but people are sick" layer.
3. **State agriculture/health pages** — distribution-filtered relays ("affecting Montana") + state-inspected products (dairy, local meat).
4. **Reputable press & trade press** — named-outlet recall reporting; Food Safety News class.
5. **Retailer hubs & manufacturer newsrooms** — lot-level and purchase-linked, fastest for "was mine affected", but non-authoritative: confirm at the agency page.
6. **Community** — Reddit, forums: discovery and corroboration, labeled community-sourced.
7. **Aggregators & apps** — recall-named private sites: leads, never endpoints.
8. **Slop** — SEO recall-list content farms (source guide §7): never cited.

A 🔴 recall-status verdict requires a tier 1–2 record fetched or snippet-verified **with specifics** (agency, date, class or reason, scope) — or ≥2 independent tier-3/4/5 confirmations with matching specifics while the agency fetch is flagged as the pending confirmation (upgrade on fetch; if the agency surface stays unreachable, the 🔴 stands on the confirmations with the access limitation named). Press-only, vague, or undated claims cap at 🟠. Lack of evidence is not evidence of safety — "no recall record found" is a statement about the search, never about the product.

## Failure handling

- **Bot-walled agency sites** (FSIS Akamai, NHTSA bot-wall — observed behavior, source guide §3): corroborate via search-engine extraction (`site:fsis.usda.gov <brand>` snippets, press relays), label the finding `access-limited`, never mark it verified-live, and never retry past the documented attempts. The user can always open the page in their own browser — say so and give the URL.
- **Thin or no record** — report honestly: "no recall record found across R1/R3/R6 with routing confirmed; absence is not verification" (🟢 or 🟡 per the rubric). Niche products, small brands, and non-US subjects legitimately have no record — that's a result, not a failure.
- **Ambiguous product identity** (common name, no brand/lot): narrow by brand + lot + date; if it stays ambiguous, that's a 🟡 with the ambiguity named — never a guess at which product was meant.
- **Mixed record** — an old concluded recall plus nothing current, or press reporting an "expanded" recall the agency page hasn't posted yet: show both, weight by tier, name the discrepancy.
- **Smoke-test false-positive guard** — if a decisive item's guard says fall through (short-code retailer texts, aggregator breadth, manufacturer's own recall microsite), it falls through; never fire a snap verdict on guarded-out evidence.
- **Subject vanished mid-check** (listing removed, post deleted, site dark) — that is itself a finding; note date/time observed.
- **User asks for perpetrator detail** — answer at recognition level; no operational guidance.
- **Session ended mid-check** — on return, read the report file, rebuild state from the ledger, resume at the next stage. In `chat` mode there is no file to rebuild from — the check restarts; surface that trade-off when the user picks `chat` (`both` keeps the file).
- **User pivots to a new subject** — mini-consolidate, start a new check file.

## Examples

**Example 1 — recall text message, smoke test snaps it.**
Input: "got a text: 'ALERT: your Gold Peak tea is recalled for contamination — pay $0.99 processing to receive your $40 refund: gp-refund[.]net'. Real?"
Stage ½ (seconds, zero searches): refund that requires paying first → S-M1 [Decisive]; link domain ≠ any Coca-Cola/retailer domain → S-M2 [Decisive]; fee-by-link to "process" → S-M3 corroborating. Snap verdict: **🔴 content authenticity — scam pattern match, High (snap)**; recall status: **not checked — `document` checks it**. Response: don't click/pay; check any real recall at fda.gov/safety/recalls or the retailer's own app; report the text (7726 spam forward + FTC). Zero searches, no file. If `document`: the routed sweep runs — Gold Peak is FDA-regulated → R1 FDA + R3 CDC + R6 press; full report written with both readouts.

**Example 2 — product name, clean documented hit.**
Input: "was Silk almond milk recalled? I have a carton in the fridge."
Stage ½: not claim-bearing content (a bare product question) → fall through immediately. Stage 1 routing: FDA-regulated food → R1 `site:fda.gov Silk almond milk recall` + R3 CDC + R6 news sweep. Suppose a documented Class II undeclared-allergen recall surfaces with dates and lot codes: verdict **🔴 recall record found — High (provisional)**, with the agency notice fetched (or snippet-verified + flagged pending fetch), current-vs-past separated, and the remedy (return/discard + refund path) in recommended actions. Coverage map shows R1/R3/R6 🔵 or 🔴, R4/R5 ⚪ with a Stage-2 plan offered to check them.

**Example 3 — lot code, bot-wall handled.**
Input: "check lot code 24-081 on my frozen ground beef, brand X."
Routing: meat → FSIS (fsis.usda.gov/recalls — Akamai-walled to automated fetchers). Stage 1: search-extraction sweep `site:fsis.usda.gov <brand> recall 24-081` + press relays; if a recall surfaces, findings are labeled `access-limited — corroborated via search extraction and <outlet> report`, the 🔴 stands on the confirmations with the limitation named, and the user is given the FSIS URL to open directly. Retailer hub (R5) checked for the lot as the non-authoritative lot-level layer. Coverage map shows R1 🔴 (access-limited), not 🔵.

**Example 4 — TikTok post claiming a recall.**
Input: "a TikTok says my air fryer brand is catching fire and recalled — is that true?"
Stage ½: post content described but no payment ask / no funnel domain visible → nothing decisive fires (a claim is not a scam tell). Stage 1: routing → CPSC (cpsc.gov/recalls, fully fetchable) + SaferProducts incident reports + R6 press + R8 community for fire reports. Verdicts delivered separately: authenticity **🟡 unverifiable** (no official confirmation the post is what it claims; no scam tells either — a panic post is not automatically fraud) and recall status per the record — 🔴 if CPSC has the recall, 🟢 "no recall record found" if not, with the fire-report cluster reported honestly as R8 community evidence either way.

**Example 5 — outbreak check, map renders.**
Input: "is the Cyclospora lettuce thing connected to the romaine I bought? where is it happening?"
Routing: produce → FDA + CDC outbreak layer. Stage 1: CDC investigation page (R3) names case counts by state; FDA recall status may be "investigation ongoing, no recall yet" → recall status **🟠 recall-adjacent** (active investigation, no recall record). Consolidation triggers the overview map (default ON): location table built from CDC/press-reported case locations — city pins where sources name cities, state diamonds for statewide counts, `n_cases` driving marker size, geocoded via the tier pipeline — rendering the interactive HTML map plus CSV/JSON table, verified in-browser before delivery. Report references all three artifacts.
